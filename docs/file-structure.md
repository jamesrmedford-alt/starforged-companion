# Starforged Companion — File Structure

What each file exports and does. This is the single authoritative file-structure
reference — there is no separate root `file-structure.md`. It covers the runtime
source tree (`src/`), the test suites, the bundled assets, and the developer
documentation under `docs/` and `rules/`.

Only `src/`, `styles/`, `lang/`, and `module.json` are bundled into the Foundry
module zip. `docs/`, `rules/`, `tests/`, `test/`, and `scripts/` are
developer-only and excluded from the release.

---

## Repository root

| File | Purpose |
|------|---------|
| `module.json` | Foundry manifest. `version` is rewritten by CI at release (the in-tree value lags the live tag). `esmodules` loads `src/index.js` and `src/integration/quench.js`. |
| `CLAUDE.md` | Auto-loaded Claude Code working instructions + bottom-of-file rules index. |
| `README.md` | Player/GM-facing overview, install, commands, cost, safety. |
| `CHANGELOG.md` | GitHub changelog. `[Unreleased]` maps to the next release after the latest tag. |
| `LICENSE.md` | CC BY-NC-SA 4.0. |
| `package.json` / `vitest.config.js` / `eslint.config.js` | npm scripts, Vitest config (coverage thresholds), ESLint flat config. |

## `src/` — runtime source

### Top level

| File | Purpose |
|------|---------|
| `index.js` | Module entry point: registers all settings + hooks, the `createChatMessage` dispatcher (every `!`/`@scene`/`\` command), the two-hook toolbar buttons, and the move/narration pipeline — whose consequence branches beyond the roller's meters and choice card are one applier, `applyOutcomeEffects` (an arrival, expedition progress, a legacy mark, the companion's health, the fight's threshold card, progress, position and end with `applyWonFightPayoff`), run in full for a rolled outcome and by Burn Momentum / Improve Result (`applyUpgradedOutcomeEffects`, their hooks' `applyEffects`) for what their upgraded outcome adds over the recorded original (issue #313); `stashPositionOnThresholdCard` puts an upgraded Enter the Fray's position on its waiting threshold card. Chat commands route through the ordered `CHAT_COMMAND_ROUTES` table, dispatched by `multiplayer/commandRouting.js`: each command carries a run-on policy — `AUTHOR` (the typist's client only), `CANONICAL_GM` (warns the author when no GM is connected), or `CLAUDE` (the keyed canonical GM when `hasKeyedActiveGM()`, else the author's client) — so a command runs exactly once, not once per connected client. Also exports, for the relay handlers and tests: `resolveVowItemCopies` (the vow a payoff targets — the roller's own vow first, then the name ladder; issue #301 B02), `resolveVowHolderActor`, `postFightVowMilestoneCard` (the won-fight card), `markLinkedVowMilestone` / `deepenLinkedConnection` (won-fight relay handlers in `moves/cardActions.js`; each returns `{ ok }`), `deepenVowConnectionOnce` (the won-fight card's 🤝 Deepen: a vow deepens its connection once — the press and the fulfilment share the vow's `fulfilPayoff.deepen` ledger step, whichever lands first pays; issue #326 D1), `payFulfilledVowNative`, `payForgedBondNative`, `postPayoffFailureCard` / `retryPayoffSteps` / `wirePayoffRetryButton` (a payoff step that did not land: the GM-whispered card, its Retry's GM side, its button — issue #306 R04; also a Burn / Improve write after its claim, an `upgrade` step, and a PC's session momentum, a `momentum` step — issue #311 P06, P08; an asset effect the world refused after a move, a `rider` step whose Retry applies that effect alone — issue #315 S08; a Begin a Session campaign clock advance the world refused, a `clocks` step (source `sessionClocks`) whose Retry saves the rolled fills through `clocks.applyClockAdvances` without rolling again — issue #316 T04), `addLegacyTicks` (the one legacy-track writer — `moves/legacyTracks.js` arithmetic; returns `{ boxes, xp, cleared }`, issue #316 T02; the box XP is owed by the copy it marked and paid once that copy is saved — `awardSavedLegacyXp`, issue #326 W52 — by writing the shared track to every PC's sheet, internal `payLegacyMark`, a mark that fills no box too, issue #326 D3), `wireWaypointOracleButton` (a waypoint match's 🔭 / 🌀 button relays `waypoint.oracle`; "🏁 Attempt to Fulfill Vow", `wireAttemptFulfillVowButton`, and the won-fight card's 🏁 relay `fulfilVow.attempt` the same way), `performRecommit` (an expedition recommit — `{ ok, reason }`, run once per offer card by `cardActions.applyRecommitOffer`; the raw-socket `registerRecommitSocket` is deleted — U20), `maybeUpdateShipPositionFromName(name, campaignState, source, { entityId })` (the shared ship-position write of `!at`, an arrival and the Entities panel's "Set as current location"; `entityId` names the place by its host id — `shipPosition.inferShipPositionFromEntityId` — the name only a fallback, issue #321 U52 / U56), `isDeniedRecapCommand`. The native sheet-roll narration hook narrates where a key lives (internal `nativeRollNarratesHere` — the keyed canonical GM, else the roller's client, issue #321 U11) and shares one subtype lookup with the payoff hook (`nativeProgressSubtypeLookup`, which reads the vendor's `bond` subtype as a connection — U21); the actor hook drops the snapshot cache on every `updateActor` (U01). `!at` and `!sector <name>` write a copy of the stored campaignState (U58). A player with no PC of their own at a table of two or more PCs is not rolled as the first PC: the pipeline whispers them a `noCharacterNotice` card and rolls nothing (internal `postNoCharacterNotice`, issue #326 D8). A Fulfill Your Vow's or Forge a Bond's miss posts a recommit offer (`postVowRecommitOfferCard` / `postBondRecommitOfferCard`); `performVowRecommit` (every open copy of the roller's vow and its journal twin) and `performBondRecommit` (the record, mirrored to the bond Items) run it on the canonical GM (issue #330 D1). |
| `api-proxy.js` | `apiPost()` — direct browser fetch to the Anthropic API with the `anthropic-dangerous-direct-browser-access` header and BYOK key injection. **All Claude calls route through here.** |
| `net/fetchWithTimeout.js` | `fetchWithTimeout()` + `DEFAULT_TIMEOUT_MS` (120s) — `fetch` bounded by an `AbortController` so a stalled request rejects instead of hanging forever. The deadline covers the whole request: the returned response's `json()` / `text()` / `arrayBuffer()` / `blob()` race the same deadline, so a body that stalls after the headers arrive also rejects (issue #300 F06). Used by `api-proxy.js` and `art/openRouterImage.js`; added after the v1.7.23 sector-creator silent hang (unbounded portrait fetch stalled, Scene never built, nothing logged). |
| `net/uploadResult.js` | `uploadedPath(response, builtPath)` — what a `FilePicker.upload` stored: the response's own path (The Forge's Assets Library URL), the built path only when the server reported success without one, else null. v13's upload resolves `false` / `undefined` / `{}` on failure instead of throwing; the sector-art, portrait, deck-plan and audio-cache uploads returned the built path for a file never written (issue #322 V26). |
| `schemas.js` | Core data schemas and enums: `STATS`, `RANKS` / `RANK_TICKS` / `rankTicks` / `rankName`, `MOVES` + `moveRollKind` (how a move resolves — "action" for a stat list, "progress" for a progress move, "none" for neither: the one classification the resolver, Take a Break's add, the move card and the Burn / Improve offers read — issue #316 T05), `toMoveId` (the MOVES key a model-named move refers to — the key or its display name in any case or separator — else null; the pacing classifier's suggestion and the PC-directed social-move check go through it, so the Roll button's `forcedMoveId` is always a real move id, issue #321 U45), `NARRATOR_CLASSES` (the MOVES contract-test anchor), `ORACLE_ODDS`, `ConnectionSchema`, `CampaignStateSchema` (incl. `questFocus` / `connectionFocus`). `MoveResolutionSchema` survives only as a documentation `@typedef` (JSDoc references still resolve). The zero-consumer `CharacterSchema`, `SessionSchema`, `ArtAssetSchema`, the `MoveResolutionSchema` object, `MISCHIEF_LEVELS`, `RELATIONSHIP_TYPES`, `ART_BACKENDS`, `IMPACTS`, `TRACK_TYPES` exports and `CampaignStateSchema.progressTrackIds` were deleted in the 2026-10 audit. |

### `audio/` — ElevenLabs narration overlay

| File | Purpose |
|------|---------|
| `index.js` | Narrator-card audio orchestrator; routes prose to voices, owns the cache-write socket. The canonical GM synthesises each clip once — one promise per content hash (internal `synthesiseToCacheOnce` → `writeToCache`), shared by its own playback and every keyless player's `audio.synth.request`, so a card played on both is billed once (issue #321 U59) — and answers `audio.synth.done { hash, path }`: a player plays that path when it names the clip's file (`…/<hash>.mp3`), so one without file-browser permission hears it (U60). A keyed default Player whose browse failed (a Player may not use the File Browser) asks the canonical GM for the cached path first — `audio.cache.ask` → `audio.cache.found { hash, path }`, lookup only, joining an in-flight synthesis, its answer never releasing a synthesis wait — before billing a new clip on their key (issue #326 W79). A keyless canonical GM never relays to itself — its Play fails at once, naming Companion Settings → About (W80). The GM serves a request only when its hash is its spec's clip key (`cacheKey(spec)`); a mismatch is refused quietly — nothing billed, nothing filed, no done signal (issue #326 W81) — and only for a segment of a narrator card in chat in the world's voices at its model and speed (`isNarratorCardClipKey`: a forged spec with an honest hash billed any voice, model, speed or text, issue #331 X51). A keyed client that is not the canonical GM relays its bytes (`audio.cache.write`, `commitToCache`); the GM files them only under the clip key of a segment of a narrator card in chat under the world's voices (internal `isNarratorCardClipKey`, an X-carded card keying nothing) and never over a clip cached or in the making (issue #330 D11). An X-carded narration card gets no Play button (U07). |
| `elevenlabs.js` | Direct browser fetch to the ElevenLabs TTS API (BYOK `xi-api-key`). |
| `segments.js` | Splits prose into narrator-vs-NPC segments via `<npc>…</npc>` markup. |
| `playback.js` | `foundry.audio.Sound` wrapper + play/queue state machine. Each `play()` from idle starts one run, tagged with a generation that `stop()` bumps: a load or segment that settles after Stop is discarded instead of playing, and a resume rejoins the run in progress rather than starting a second loop (issue #300 F08, F09). |
| `cache.js` | Content-addressed cache (`worlds/<id>/audio/...`); Forge-aware upload/lookup. `lookupDetailed(hash)` → `{ path, browsed }` also says whether this client could browse the directory at all (`lookup` returns its path). |

### `character/` — Actor integration + chronicle

| File | Purpose |
|------|---------|
| `actorBridge.js` | **The only** interface for foundry-ironsworn Actor reads/writes (health, spirit, supply, momentum, impacts, XP, legacies). `readCharacterSnapshot` (cached per actor; dropped on every `updateActor` — any actor, whoever owns it, issue #321 U01 — and on the actor's Item changes) also carries the `grantedRewards` the narrator's CHARACTER block lists (issue #286 C5). `readVows` / `readConnections` give each vow's and bond's `rank` as a rank name (`rankName` over the vendor's numeric rank, issue #321 U62), and `readVows` each copy's `vowId` (U02). `advanceVowClocks(actor, { by, lockstep })`: one `lockstep` map carried through every PC's call of a single advance sets a shared vow's later copies to the value its first copy reached, and each entry carries its `vowId` (U55). `readMomentumState` — momentum and its bounds read live (value, min, max, reset, impact count) from the one bounds derivation (`momentumBounds`: the vendor's `momentumMax` / `momentumReset` getters, else the vendor's formula over the sheet's base fields — read only: the module never writes `system.momentum.max` / `resetValue`, the bases the getters deduct the impacts from, and `recalculateMomentumBounds` only clamps momentum to the new maximum — issue #316 T01); the burn preview and burn apply read it (issue #300 F03), and the move pipeline and `!bond` read the roller's momentum with it when they roll (a negative one can cancel the action die — issue #311 P01). `revertVowClocksForBurn` returns the rewinds the world refused (issue #311 P06). `setBondItemTicks` / `setBondItemRank` / `setBondItemLost` mirror a connection onto the PCs' bond Items through `bondItemsFor`: an Item keyed by the record's `_id` matches that id alone, the name only an unkeyed Item and only the PC's one of that name (issue #314 Q04). `setBondItemLost` writes a severed record's loss as `flags[MODULE].lost`, which `readConnections` reports as `lost` (issue #330 D10). The sheet's legacy tracks: `readSheetLegacy` / `writeSheetLegacy` (`system.legacies.<track>`, ticks ever marked — the Starforged sheet's Legacies tab, where the shared tracks are mirrored) and `SHEET_LEGACY_TRACKS`; the snapshot's `xp` is the XP that sheet shows (earned from the legacies, less spent); `awardXP` (`system.xp`, the classic sheet's field) is deleted — issue #326 D3. Companions: `listCompanionAssets` / `getCompanionAsset` / `readCompanionHealth` / `applyCompanionHealthChange` — a companion's health is its Companion asset's track (`system.track.value`), the one write a consequence's companion health goes through (issue #309 N03). `setVowItemTrack` writes a vow Item's ticks and rank the way the Item holds its rank (a vendor number or a name) — the vow recommit (issue #330 D1). |
| `chronicle.js` | Character chronicle schema + CRUD (`addChronicleEntry`, `getChronicleEntries`, `updateChronicleEntry`; the panel's `setChronicleEntryPinned` / `setChronicleEntryType` / `deleteChronicleEntry`, each changing one entry by id on the entries as stored when it writes — issue #306 R02; `CHRONICLE_AUTO_TYPES`, the five the automatic writer picks from, and `CHRONICLE_ENTRY_TYPES`, every type — those five and the hand-set `vow` / `legacy` / `annotation` — which the panel's type select offers and a re-type accepts: issue #322 V33). Every client asks for a change with `requestChronicleEdit(actorId, edit)` — the `"chronicle.edit"` relay; `applyChronicleEditFromRelay` applies it on the canonical GM, the Chronicle's one writer (a player's client cannot write the GM's journal — issue #306 R11), refusing a requester who neither is a GM nor owns the PC, GM-only re-type / delete, a player's non-annotation add; an actor's writes on one client run one at a time (`writeChronicle`, R02). A chronicle is the Actor's by its journal's `chronicleActorId` flag, never by the "Chronicle — {name}" label (issue #301 B03): a rename keeps the history, namesakes keep separate chronicles, a history an earlier rename split over two journals reads merged and folds into one on the next write, and an unflagged legacy journal is adopted only when one character has its name. |
| `chronicleWriter.js` | Claude call writing chronicle entries from move resolutions; the write goes to the canonical GM (`requestChronicleEdit`, issue #306 R11). Its types are `chronicle.js`'s `CHRONICLE_AUTO_TYPES` (anything else is written as a `moment`). |
| `chroniclePanel.js` | Chronicle UI panel (ApplicationV2). Every read goes through `chronicle.js`, every edit through `requestChronicleEdit` (applied by the canonical GM — issue #306 R11); pin, delete and re-type change one entry by id, never save the panel's own copy (R02). `registerChroniclePanelHooks` (ready) re-renders the open panel when its chronicle's page changes — a relayed edit has no ack. `openChroniclePanel()` with no actor opens the viewer's own PC's (`speaker.resolveUserActorId`), not the first PC's (issue #321 U23). |

### `clocks/` — campaign & tension clocks

| File | Purpose |
|------|---------|
| `clocks.js` | `!clock` commands (`new`/`advance`/`fill`/`reset`/`remove`/`list`) + ApplicationV2 panel + advance-on-oracle odds. `advanceTensionClocksForPayThePrice` / `revertTensionClocksForBurn`, `advanceCampaignClocksForBeginSession` (works on a copy and keeps its rolls when the write is refused — `saved: false` and the fill rolled to on each advanced result — issue #316 T04), `applyClockAdvances` (the GMs' Retry of such an advance: each clock to at least its rolled fill, once, nothing rolled), `retireClock` (`active: false`, kept and shown as retired — a completed scene challenge's paired clock, issue #316 T03) / `removeClock` (shared by `!clock remove`, the panel's ✕ and a removed scene challenge). | `payThePriceClocks.js` | `advanceClocksOnPayThePrice` (tension clocks + each PC's vow countdown clocks, one segment per Pay the Price; GM-only — called directly by the move pipeline, which keeps the return for the burn reversal) and `advanceClocksForPayThePriceRelay` (gmRelay `payThePrice.advanceClocks`, so a player-typed `!ptp` advances the clocks once, on the canonical GM). ### `entities/` — entity records & discovery

| File | Purpose |
|------|---------|
| `registry.js` | Host-document dispatch: routes reads/writes to Actor vs JournalEntry storage. `hasSheetNotes` / `withSheetNotes`: an NPC card's or ship's notes are its sheet's Notes tab (`system.notes`) — the record getters read it there (issue #329 X12). `ENTITY_ID_LISTS` + `unionIdList` (the campaignState id lists, unioned by persistResolution's merge and the sector store); `registerEntityIdInStore` — every creator registers its new id on the latest stored campaignState instead of writing the caller's copy whole (issue #300 F14), through `registerEntityId(campaignState, listKey, id, { persist })`: the store first, and only once the world took it does the creator push the id onto its copy — often the cached setting, where a refused write left an id the world never registered (issue #331 X35; `storeArtAsset` the same for `artAssetIds`). `writeEntityFlag` re-renders a journal-hosted faction's or creature's page body from the record it writes (`rerenderEntityPageBody`, also called by `faction.updateFaction`) — the body was rendered only at creation (issue #322 V31). |
| `connection.js`, `ship.js`, `settlement.js`, `planet.js`, `location.js`, `faction.js`, `creature.js` | Per-type entity record CRUD (ships/settlements/planets/locations on Actors; others on JournalEntry pages). The art pipeline links portraits through the registry (`art/generator.js` → `writeEntityFlag`); the zero-consumer per-type `setPortraitId` / `setPortraitSourceDescription` / `isReadyForArtGeneration` helpers and `creature.updateCreature` were deleted in the 2026-10 audit. `ship.js`: `repairIntegrity` / `clearBattered` are live (`!repair`); `changeIntegrity` is the one writer for a consequence's or an asset effect's integrity change (Withstand Damage's choices, asset effects) — a rise refused while battered, a loss always landing; reports, never throws (issue #315 S05); `isShipBattered` reads the canonical native `system.debility.battered` (the starship sheet's toggle and the suffer dialog use only that field — the flag's `battered` is a write-through mirror kept by `updateShip`); `sufferDamage` is still `// UNWIRED: #216 Phase D`. `seedStarshipActor` / `seedConnectionActor` take `finalizedAt` (the Finalise stamp, written in the seed's own update — issue #311 P07). Both write only the fields they seed, by flag path, onto the record as it is when the write lands — never the snapshot read before their Notes call (issue #326 W69 the connection's, issue #331 X32 the ship's: a position, integrity, the command-vehicle flag or a rename landing during the call stands). `isLoneShipCandidate(ship)` — false for a ship the narration introduced and the GM confirmed from a draft card (`ShipSchema.npcShip`, set by draft Confirm): every lone-ship fallback skips it (`getCommandVehicle`, `getCommandVehicleActorId`, `abilityScanner.getCommandVehicleActor`, the narrator's ship line, a no-target `!ship envision` / `history`, Campaign Start's `findCommandVehicle`), so a confirmed pirate cutter never displaces the players' ship (issue #321 U26; the `isCommandVehicle` flag still wins). |
| `finalize.js` | The entity finalize lifecycle (T1): `finalizeEntity(typeKey, hostId, campaignState, { force })` — settlement / planet / location get a grounded flavour pass; ship and connection run their seed (`finalizeViaSeed`). One completion contract for both: a record with `finalizedAt` is left as it is unless `force` (Regenerate flavour), and a successful finalize stamps it, so the Entity Panel switches to Regenerate (issue #311 P07 — a ship's repeat Finalise rewrote its Notes). A ship whose Notes already hold text (the Auto-Seed's introduction, the GM's own) is stamped by its first Finalise, nothing else, as a seeded connection is (issue #331 X34); one with empty Notes is seeded; ↻ Regenerate re-seeds. `finalizeEntityArtOnly` stamps and triggers a portrait without the Claude call (sector creator). |
| `shipEnvision.js` | On-demand ✦ Envision / 📜 History for ships. Rolls supplementary oracles beyond the seed (captain, crew, agenda, initial contact) + Action+Theme backstory beats; narrator-prose composer; chat-command predicates + handlers (`!ship envision` / `!ship history`, routed `RUN_ON.CLAUDE` — the keyed canonical GM when one is connected, else the author, whose client posts the card but skips the GM-only notes write with a debug line); idempotent dated-subsection notes append. |
| `entityExtractor.js` | Combined detection pass: extracts entities from narrator output + World Journal routing rule; renders draft Confirm/Dismiss cards. `appendGenerativeTierUpdates` records a matched entity's significant new developments to its card, salience-gated (`TIER_SALIENCE_FLOOR`, fail-open) and biased toward actions over trivia, and saves them on the host document through the registry. `promoteNewEntityLedgerSubjects` re-keys the scene ledgers' text-subject facts to a new entity's host id (draft Confirm, make_a_connection auto-create, inciting vow-target create — and a placeholder's rename, for the facts recorded under its new name, issue #326 W68). Draft Confirm runs once per draft on the clicking GM (an in-flight guard, issue #302); each Confirm / Dismiss writes only its own row's status, one write at a time per card, on the live card (internal `setDraftStatus`), and Confirm creates nothing when an entity of that name and type exists (`entityExistsForName`) — issue #321 U25. A narrator write never overturns a GM's ruling: `recordLoreDiscovery` with `narratorAsserted: true` leaves an entry the GM ruled a rumour or dismissed from review (internal `isGmRuledLore`) as it was, and `promoteLoreToConfirmed(…, { byNarrator: true })` — the capture's "lore confirmed" — does not promote one (issue #330 D9). `restoreStruckLore(truthId)` is `retractSessionLore`'s inverse — the entries a lifted strike retracted, by `retractedByTruth`, back to the confirmation they had (issue #331 X31). Every write to an existing page goes through `upsertPage` or `writeEntryPage(page, flagKey, data)` (the record flag, then its re-rendered body — a refused body write warned), so the body players read follows a severity change, a confirm, a strike and the panel's Dismiss; a retracted lore entry renders "Retracted by the table." (issue #331 X30). |

Contradictions: a lore catch gets Review / Override / Dismiss; a fact-continuity catch (◈ Narrative Review, `factContinuityReview`) gets Correct… (`openCorrectionDialog`) / Dismiss, and Override refuses it (issue #325 W34). |
