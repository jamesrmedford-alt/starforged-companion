# Starforged Companion — File Structure

What each file exports and does. This is the single authoritative file-structure
reference — there is no separate root `file-structure.md`. It covers the runtime
source tree (`src/`), the test suites, the bundled assets, and the developer
documentation under `docs/` and `rules/`.

Only `src/`, `styles/`, `lang/`, and `module.json` are bundled into the Foundry
module zip. `docs/`, `rules/`, `tests/`, `test/`, and `scripts/` are
developer-only and excluded from the release.

---

## Repository root

| File | Purpose |
|------|---------|
| `module.json` | Foundry manifest. `version` is rewritten by CI at release (the in-tree value lags the live tag). `esmodules` loads `src/index.js` and `src/integration/quench.js`. |
| `CLAUDE.md` | Auto-loaded Claude Code working instructions + bottom-of-file rules index. |
| `README.md` | Player/GM-facing overview, install, commands, cost, safety. |
| `CHANGELOG.md` | GitHub changelog. `[Unreleased]` maps to the next release after the latest tag. |
| `LICENSE.md` | CC BY-NC-SA 4.0. |
| `package.json` / `vitest.config.js` / `eslint.config.js` | npm scripts, Vitest config (coverage thresholds), ESLint flat config. |

### `art/` — entity portrait generation

| File | Purpose |
|------|---------|
| `generator.js` | Portrait pipeline (generate-once → one regeneration → locked). Generated on a GM's client only (internal `canKeepPortrait`: `generatePortrait` / `regeneratePortrait` return null elsewhere before anything is requested or billed — storing, linking and attaching a portrait are GM writes, so a player's click paid for an image that was then lost; issue #321 U33). `generatePortrait` stores nothing when its entity's host document is gone by the time the image returns — a connection the X-Card took back meanwhile (XCARD-LATE-CAPTURE) — and returns any portrait the record names that is not locked: only `regeneratePortrait` replaces one. One first portrait per entity: one image at a time for an entity on a client (internal `_portraitsInFlight`, claimed before the image call and released in a `finally` — a second generation waits for the first and gets its portrait), and an image that comes back after another portrait was linked meanwhile (another GM's) leaves that one standing and is not stored (known-issues PORTRAIT-LATE-FIRST-GENERATION: the panel's Generate during a new card's seed bought a second image, and a late first portrait replaced a locked regenerated one). A first portrait is put on the Actor only once the record names it: a refused link tells the GM and leaves the Actor as it was, and the next generation links the stored portrait (`storage.findEntityPortrait`) instead of buying one (known-issues FIRST-PORTRAIT-LINK-REFUSED). `regeneratePortrait` claims the one regeneration on the portrait the record names (`regenerationUsed`) before its image is bought, gives it back only when the image could not be made, and spends it when the new portrait is not saved — the earlier one stays, locked, the GM told; internal `linkPortraitToEntity` reports whether the record names the portrait (known-issues REGEN-LINK-REFUSED-SECOND-REGEN: a refused link left the record on an unmarked portrait and a second regeneration was billed). |
| `openRouterImage.js` | OpenRouter image client; decodes inline base64. **Sole image-provider call site.** |
| `promptBuilder.js` | Builds image prompts from entity descriptions. A connection's prompt leads with the gender descriptor of the pronouns the card holds now (`withCurrentGenderLead` — the seed baked the set it established into the portrait source, issue #335 Y13). |
| `storage.js` | Portrait persistence (base64 flag storage). `storeArtAsset` adds its `artAssetIds` index entry to the latest stored campaignState, never the caller's whole copy (issue #300 F14) — read at its turn on the client's campaignState write chain, and not written when the store already names the entry (ART-INDEX-WRITE-OFF-CHAIN, as is `deleteEntityArtAssets`' index write); a refused index write leaves the asset unindexed but returned, so its portrait is still linked to the entity (`loadArtAsset` finds it by its journal entry's flags) and never bought twice (issue #337 Y34). `deleteEntityArtAssets(entityType, entityId, { portraitId })` deletes an entity's portrait entries (a superseded one too) and drops their index entries on a copy of the latest store — canonical GM only; a refused index write is logged, never thrown — for the X-Card's removal of an unused connection (XCARD-CONNECTION-PORTRAIT-ORPHAN). `findEntityPortrait(entityType, entityId)` — the newest portrait stored for an entity that no regeneration superseded; the generator links it for a record that names no portrait it can load, so a first portrait whose link the world refused is saved by the next generation without buying another (known-issues FIRST-PORTRAIT-LINK-REFUSED). |
| `notesPortrait.js` | The portrait block embedded at the top of a connection's or ship's Notes: `PORTRAIT_BLOCK_RE` (the marker div `withPortraitInNotes` writes and replaces). A re-seed (↻ Regenerate flavour) keeps it, as it keeps everything on the tab but its own introduction (`entities/seedIntro.js`), since the existing portrait is not attached again (issue #322 V30). |

### `audio/` — ElevenLabs narration overlay

| File | Purpose |
|------|---------|
| `index.js` | Narrator-card audio orchestrator; routes prose to voices, owns the cache-write socket. Its GM-side work — answering a keyless client's request or ask, filing a relayed clip, caching its own — runs on the audio GM (`gmGate.isAudioGM`: the lowest-id active GM holding an ElevenLabs key, else the canonical GM; the canonical GM is chosen by the Claude key, so a keyless one answered every keyless Play "no clip" while a keyed co-GM stood down — issue #342 Z67); "the canonical GM" below is that GM. The canonical GM synthesises each clip once — one promise per content hash (internal `synthesiseToCacheOnce` → `writeToCache`), shared by its own playback and every keyless player's `audio.synth.request`, so a card played on both is billed once (issue #321 U59) — and answers `audio.synth.done { hash, path }`: a player plays that path, so one without file-browser permission hears it (U60) — only when the GM's cache could name it (`cache.isCachePathFor`, also for `audio.cache.found`; any other path is no answer, and the player waits on for the GM's — issue #337 Y42). A keyed default Player whose browse failed (a Player may not use the File Browser) asks the canonical GM for the cached path first — `audio.cache.ask` → `audio.cache.found { hash, path }`, lookup only, joining an in-flight synthesis, its answer never releasing a synthesis wait — before billing a new clip on their key (issue #326 W79). A keyless canonical GM never relays to itself — its Play fails at once, naming Companion Settings → About (W80). The GM serves a request only when its hash is its spec's clip key (`cacheKey(spec)`); a mismatch is refused quietly — nothing billed, nothing filed, no done signal (issue #326 W81) — and only for a segment of a narrator card in chat in the world's voices at its model and speed (`isNarratorCardClipKey`: a forged spec with an honest hash billed any voice, model, speed or text, issue #331 X51). A keyed client that is not the canonical GM relays its bytes (`audio.cache.write`, `commitToCache`); a GM that holds an ElevenLabs key files none — it makes its own clips (issue #338 D10) — and a keyless GM files them only under the clip key of a segment of a narrator card in chat under the world's voices (internal `isNarratorCardClipKey`, an X-carded card keying nothing) and never over a clip cached or in the making (issue #330 D11). An X-carded narration card gets no Play button (U07). A chat message counts as a narrator card — its Play button, auto-play, and the clip key a relayed synthesis or cache write is checked against — only when a GM posted it while a keyed GM is connected (`hasKeyedActiveGM`); a player-authored one only with no keyed GM connected and no longer than the narrator can return (Narration Max Tokens × 4 characters) — any user may post a message with narrator flags (internal `countsAsNarratorCard`, issue #342 D8). |
| `elevenlabs.js` | Direct browser fetch to the ElevenLabs TTS API (BYOK `xi-api-key`). |
| `segments.js` | Splits prose into narrator-vs-NPC segments via `<npc>…</npc>` markup. |
| `playback.js` | `foundry.audio.Sound` wrapper + play/queue state machine. Each `play()` from idle starts one run, tagged with a generation that `stop()` bumps: a load or segment that settles after Stop is discarded instead of playing, and a resume rejoins the run in progress rather than starting a second loop (issue #300 F08, F09). |
| `cache.js` | Content-addressed cache (`worlds/<id>/audio/...`); Forge-aware upload/lookup. `lookupDetailed(hash)` → `{ path, browsed }` also says whether this client could browse the directory at all (`lookup` returns its path). `isCachePathFor(hash, path)` — whether a path is one the cache can name for that clip: the world's `worlds/<world>/audio/<xx>/<hash>.mp3`, or a Forge Assets Library URL ending in `/<hash>.mp3` (the bound on the GM's relayed answers, issue #337 Y42). |

### `batch/` — Batch Mode rounds (issue #340)

|------|---------|
| `round.js` | A round as data, pure: `ROUND_PHASE` (collecting → rolling → upgrading → narrating → closed), `ENTRY_STATUS`, `ENTRY_ERROR` (an entry's error said as such — its character gone), `READING_KIND`, `RoundRefusal`. `participantsFrom({ users, pcs })` (every connected user with a PC of their own — a GM only with an assigned PC), `createRound` / `addParticipant` / `closeRound` / `nextRoundNumber` / `markModeOffAfter`; the entry transitions `submitEntry`, `withdrawEntry`, `passEntry` (both keep a card's move — an offer beside the entry, or the card-move entry itself, offered now), `recordReading` / `readingFailed` (only while the submission is still the entry's), `confirmEntry` (joins the end of the confirm order), `rereadEntry` ("Roll a move instead", or the card's offered move), `offerForcedMove` (a card button's move: the entry, or an offer beside one submitted — its chat message's id kept on it; a move the card owes, `isOwedEntry` — the resist roll at 0 — takes the entry even beside a written action, which is `setAside` for its author's next-round draft, and is refused Withdraw / Pass / a rewrite / a re-read), `takeCardMoves` (the card moves a round leaves behind as it stops collecting — an offer not chosen, a card-move entry it does not roll — handed back by message id to be held for the next round; only Keep mine, `confirmEntry`, drops an offer); `validateChoices` (only abilities, stats and targets the reading offered) and `cleanSubmissionText` (`ROUND_TEXT_MAX`); resolution — `readyToResolve` (every connected participant ready or passed), `readingsInFlight`, `beginResolution`, `actingOrder` / `fixActing` (confirm order; Send now adds readings not confirmed, used as read), `markRolled` / `markRecorded` / `markRefused` / `allSettled`, `beginUpgrades` / `decideUpgrade` / `keepUndecidedUpgrades` / `upgradesSettled` / `undecidedUpgrades`, `beginNarration` / `claimNarration`; `recoveryPlan` (recorded, rolled-not-recorded, to roll). | `roundView.js` | What each viewer's Round window shows, pure: `buildRoundView(round, viewer, ctx)` — the viewer's own entry (editable until the round resolves; Reading · To confirm · Ready · Passed · Rolled · Deciding upgrade), the other players' entries once Ready (never a pass or an unsubmitted draft), a GM's every reading, who the round waits for, Send now (disabled under the X-Card, with the reason) and Discard; the banners for no session, no GM, no keyed GM and the X-Card (`ROUND_NOTICES`). |

| `driver.js` | The canonical GM's round driver. Settings `batchMode.enabled` / `batchMode.round` (world) and `batchMode.draft` (client), with `onBatchModeToggled` / `onRoundChanged` / `onRoundDraftChanged` listeners; `queueRoundWrite` (the round's one write chain: a pure transition on the latest stored value, no await between read and set); `openRoundIfDue` (get-or-create by session; also run when the canonical GM hears a round's close, whoever closed it) and `closeCollectingRound` (End a Session, Discard, the mode off — the authors told); a roller who isn't connected, or whose choice card closed the upgrades, is kept), `narrateRound`, close, open the next — then, off the advance pass so a GM's rider prompt holds no later round, each entry's `finishMove`, run only by the close that ends the round; a step the world refuses stops the pass and is said to the GMs); `requestSendNow` (while the round rolls or narrates it runs a stopped pass again; one waiting on a busy lock is for the round it was pressed for — a round closed meanwhile, by a Discard, End a Session or the mode off, takes it with it); `acceptRoundUpgrade` (an upgrade of an entry not yet narrated hands the round its resolution); `handleBatchModeLine` (typed chat is table talk; a card button's move becomes its roller's entry, or waits for the next round — as does one a round resolves or closes without, `takeCardMoves` at `fixActing` and `closeCollectingRound`; `recoverRound` (on `ready`, when the resolving GM leaves, when a user or a keyed GM joins: a resolving round of an ended session is closed only on the first two; the session a load is replacing — `sessionNeedsMint` at `ready` — is over until its mint lands, so none of its rounds reads, resolves or opens); `registerBatchModeDriver`; `configureBatchDriver` / `setBatchFreeFlowRunner` (index.js's lock paths — claim, release and `moveLockFree`, which a round waiting for a busy lock reads again once its wait is marked, ROUND-LOCK-WAIT-MARKED-LATE — and free-flow pipeline);
